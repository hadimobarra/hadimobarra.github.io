29:Tac1,<h2 id="the-problem">The problem</h2>
<p>Data teams bring large files into an ETL platform: CSV, TSV, JSON and Excel, up to several gigabytes. A single HTTP request is a poor fit. If the connection drops near the end, the whole transfer starts over, and the user loses trust in the tool.</p>
<h2 id="constraints">Constraints</h2>
<ul>
<li>A dropped connection must not lose progress.</li>
<li>People need to pause and resume on purpose, not only after errors.</li>
<li>The browser must never read a multi-GB file into memory.</li>
<li>The interface has to say what is going on: uploading, paused, retrying or done.</li>
</ul>
<h2 id="decisions">Decisions</h2>
<p><strong>Use an open protocol.</strong> TUS is a small, documented standard for resumable uploads over HTTP, with client and server implementations in many languages. That is safer than inventing a private chunking format and maintaining both ends of it.</p>
<p><strong>Use Uppy for state.</strong> Uppy handles the file queue, restrictions, progress and pause state, and its TUS plugin drives the transfer. React renders that state instead of owning it.</p>
<p><strong>Let the server be the source of truth.</strong> The client doesn't guess how much arrived. After any interruption it asks.</p>
<h2 id="how-resuming-works">How resuming works</h2>
<p>Three requests carry the protocol:</p>
<ol>
<li><code>POST</code> creates the upload and returns its URL.</li>
<li><code>PATCH</code> sends bytes, starting at an <code>Upload-Offset</code>.</li>
<li><code>HEAD</code> asks the server which offset it has stored.</li>
</ol>
<p>After a failure, the client sends <code>HEAD</code>, receives the stored offset, slices the file from that byte and continues with <code>PATCH</code>. <code>Blob.slice()</code> is lazy, so the file is read piece by piece.</p>
