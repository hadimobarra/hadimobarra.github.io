10:Tcc9,<h2 id="why-the-event-loop-still-trips-up-senior-engineers">Why the event loop still trips up senior engineers</h2>
<p>Most of us learned the event loop as "JavaScript is single-threaded, async things go into a queue". That model is good enough until it isn't: a <code>Promise</code> chain that starves the renderer, a <code>setTimeout(fn, 0)</code> that fires <em>after</em> a frame you expected it to beat, or a <code>requestAnimationFrame</code> callback that runs twice as often as you thought.</p>
<p>This article builds a precise model based on the HTML specification, then uses it to answer real production questions.</p>
<h2 id="the-model-in-one-picture">The model in one picture</h2>
<p>Every browser tab's main thread runs a loop that, simplified, looks like this:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-js"><span class="hljs-keyword">while</span> (<span class="hljs-literal">true</span>) {
  <span class="hljs-comment">// 1. Run ONE task (macrotask) from a task queue</span>
  <span class="hljs-keyword">const</span> task = <span class="hljs-title function_">pickTaskFromSomeQueue</span>();
  <span class="hljs-keyword">if</span> (task) <span class="hljs-title function_">run</span>(task);

  <span class="hljs-comment">// 2. Drain the ENTIRE microtask queue</span>
  <span class="hljs-keyword">while</span> (microtaskQueue.<span class="hljs-property">length</span>) {
    <span class="hljs-title function_">run</span>(microtaskQueue.<span class="hljs-title function_">shift</span>());
  }

  <span class="hljs-comment">// 3. Maybe render (roughly every 16.7ms on a 60Hz display)</span>
  <span class="hljs-keyword">if</span> (<span class="hljs-title function_">isRenderingOpportunity</span>()) {
    <span class="hljs-title function_">runResizeAndScrollSteps</span>();
    <span class="hljs-title function_">runAnimationFrameCallbacks</span>(); <span class="hljs-comment">// requestAnimationFrame</span>
    <span class="hljs-title function_">recalcStyle</span>();
    <span class="hljs-title function_">layout</span>();
    <span class="hljs-title function_">runResizeObserverCallbacks</span>();
    <span class="hljs-title function_">paint</span>();
  }

  <span class="hljs-comment">// 4. If idle, run requestIdleCallback callbacks</span>
}
</code></pre><span class="code-lang">js</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<p>Three rules fall out of this pseudo-code, and nearly every event-loop puzzle reduces to them:</p>
<ol>
<li><strong>One task per turn.</strong> Tasks never run back-to-back without giving microtasks (and possibly rendering) a chance.</li>
<li><strong>Microtasks drain completely.</strong> If a microtask schedules another microtask, that one runs too, before anything else.</li>
<li><strong>Rendering is opportunistic.</strong> The browser decides when a frame is due; your code can only <em>ask</em> to run right before it, via <code>requestAnimationFrame</code>.</li>
</ol>

<h2 id="tasks-vs-microtasks">Tasks vs microtasks</h2>
<p><strong>Tasks</strong> (often called macrotasks) come from: <code>setTimeout</code>/<code>setInterval</code>, user input events, <code>MessageChannel</code> messages, network callbacks, and parsing HTML.</p>
<p><strong>Microtasks</strong> come from: promise reactions (<code>.then</code>, <code>await</code> continuations), <code>queueMicrotask</code>, and <code>MutationObserver</code>.</p>

<h2 id="await-is-just-a-microtask-boundary"><code>await</code> is just a microtask boundary</h2>

<h2 id="a-debugging-checklist">A debugging checklist</h2>
<p>When something runs in the "wrong" order, ask:</p>
<ol>
<li><strong>Is it a task or a microtask?</strong> Promise reactions always beat timers.</li>
<li><strong>Did the microtask queue drain?</strong> A long chain of <code>then</code>s delays everything else, including paint.</li>
<li><strong>Do I need a frame or a task?</strong> Visual changes belong in <code>rAF</code>; yielding for responsiveness needs a task (<code>scheduler.yield</code>, <code>setTimeout</code>, <code>MessageChannel</code>).</li>
<li><strong>Is the tab in the background?</strong> <code>rAF</code> stops and timers are throttled.</li>
</ol>
<h2 id="conclusion">Conclusion</h2>
<p>Learn the loop as three rules — one task per turn, microtasks drain fully, rendering is opportunistic — and most "weird async bugs" become predictable. That predictability is what lets you break long work into chunks, keep Interaction to Next Paint low, and write animations that stay smooth on every refresh rate.</p>
