<h2 id="what-made-it-a-good-first-issue">What made it a good first issue</h2>
<ul>
<li><strong>A clear symptom.</strong> "Image export is blank on Safari" is either fixed or not.</li>
<li><strong>People affected.</strong> The <a href="https://github.com/apache/superset/issues/28713">issue</a> had been open since May 2024.</li>
<li><strong>A cause that can be explained.</strong> The capture library documents Safari as unsupported, and says why. A PR that explains why something broke is much easier to review than one that only makes it stop.</li>
</ul>
<p>A small fix to an important problem is a better first contribution than a big one to a problem nobody reported.</p>
<h2 id="what-to-put-in-the-description">What to put in the description</h2>
<p>Reviewers of large projects read many PRs. The description answered four questions:</p>
<ol>
<li>What's broken, and for whom?</li>
<li>Why? With a link to the library's own documentation.</li>
<li>What does this change, and what does it deliberately leave alone?</li>
<li>How can you check it?</li>
</ol>
<p>The third one matters most. Saying "other browsers keep their existing path" tells a reviewer where the risk is <em>not</em>. The first review picked up on exactly that.</p>
<h2 id="three-times-changes-requested">Three times "changes requested"</h2>
<p>The first review arrived the same day. It called the root-cause analysis correct, and then asked whether map charts would still be blank, because I had skipped a step the old path took. They would have been.</p>
<p>It was a scenario I hadn't covered, from someone who knows what else the code has to do. The pattern repeated:</p>
<div class="table-wrap" tabindex="0"><table>
<thead>
<tr>
<th>Round</th>
<th>What the review found</th>
</tr>
</thead>
<tbody>
<tr>
<td>1</td>
<td>WebGL charts might still export blank. Load the library lazily. Keep the table print layout</td>
</tr>
<tr>
<td>2</td>
<td>Map layers live in a <em>second</em> canvas, which still isn't preserved</td>
</tr>
<tr>
<td>3</td>
<td>The capture size and CORS points are resolved. The second canvas is the last blocker</td>
</tr>
<tr>
<td>4</td>
<td>Approved, with a request to check on real Safari</td>
</tr>
</tbody>
</table></div>
<p>Hardly any of it was about style. Behind each blocking point was a user who would still have had the bug.</p>
<p><strong>Answering is part of the work.</strong> For each blocking comment I either changed the code and named the commit, or explained why not. One automated reviewer wanted images from other origins included. I replied that allowing them would make the whole export fail, so leaving them out was the better trade. Disagreeing with a reason is fine. Ignoring isn't.</p>
<h2 id="saying-i-cant-test-this">Saying "I can't test this"</h2>
<p>Round four asked me to check the result on real Safari. I don't have access to a Mac. I wrote that plainly and asked whether someone else could.</p>
<p>A reviewer did, carefully, and found a problem: the new mode exposed a version mismatch between two of Superset's dependencies. Without an honest "I can't verify this", that test might not have happened before release. The mismatch was in the lockfile rather than in my code, and the main branch has since aligned the versions.</p>
<p>An approval is easy to accept in silence. Saying what you couldn't check is more useful to everyone who will run the code.</p>
<h2 id="what-i-would-do-differently">What I would do differently</h2>
<ul>
<li><strong>Check access to the environment first.</strong> For a Safari bug, the first question is "who has Safari?" Ask in the issue before starting.</li>
<li><strong>Read the code path around the change.</strong> The table layout and the canvas copying that round one asked about were already in the path I had bypassed.</li>
<li><strong>Write the failing test first.</strong> It forces you to say exactly what's broken. For my later <a href="/blog/never-trust-json-parse-in-render/">OpenMetadata fix</a>, the tests found two more bugs.</li>
<li><strong>Keep commits by concern.</strong> Separate commits let reviewers look only at what changed since last time.</li>
</ul>
<h2 id="if-youre-about-to-open-your-first">If you're about to open your first</h2>
<ol>
<li>Run the project and reproduce the bug before anything else.</li>
<li>Find the contribution guide and the PR template. Follow them literally.</li>
<li>Make the smallest change that fixes the root cause.</li>
<li>Expect several rounds. Requested changes mean someone is taking it seriously.</li>
<li>Reply to every comment, in the code or in words.</li>
<li>Say what you couldn't verify.</li>
</ol>
<p><a href="https://opensource.guide/how-to-contribute/">GitHub's open source guide</a> covers the basics well, and Superset's <a href="https://superset.apache.org/developer-docs/">contributor documentation</a> is a good example of what large projects expect.</p>
<h2 id="conclusion">Conclusion</h2>
<p>The merged change adds about 150 lines of production code, and more than twice that in tests. The value was in having people who know the system better than I do point at what I couldn't see.
