<h2 id="why-you-should-always-forward-with-reflect">Why you should always forward with <code>Reflect</code></h2>
<p><code>Reflect</code> has one method per trap with the exact same signature. It performs the <em>default</em> behaviour. Using it instead of <code>target[key]</code> matters because of the <code>receiver</code> argument:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-js"><span class="hljs-keyword">const</span> base = {
  <span class="hljs-attr">_name</span>: <span class="hljs-string">"base"</span>,
  <span class="hljs-keyword">get</span> <span class="hljs-title function_">name</span>() {
    <span class="hljs-keyword">return</span> <span class="hljs-variable language_">this</span>.<span class="hljs-property">_name</span>;
  },
};

<span class="hljs-keyword">const</span> proxy = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Proxy</span>(base, {
  <span class="hljs-title function_">get</span>(<span class="hljs-params">target, key, receiver</span>) {
    <span class="hljs-keyword">return</span> target[key]; <span class="hljs-comment">// ❌ the getter runs with this === target</span>
  },
});

<span class="hljs-keyword">const</span> child = <span class="hljs-title class_">Object</span>.<span class="hljs-title function_">create</span>(proxy);
child.<span class="hljs-property">_name</span> = <span class="hljs-string">"child"</span>;
child.<span class="hljs-property">name</span>; <span class="hljs-comment">// "base" — wrong!</span>
</code></pre><span class="code-lang">js</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<p>When <code>child.name</code> walks up the prototype chain into the proxy, <code>receiver</code> is <code>child</code>. <code>target[key]</code> drops it and calls the getter on <code>target</code>. <code>Reflect.get(target, key, receiver)</code> preserves <code>this === child</code> and returns <code>"child"</code>. The same applies to <code>set</code> and setters.</p>
<h2 id="trap-invariants-what-you-cannot-lie-about">Trap invariants: what you cannot lie about</h2>
<p>Proxies can't violate certain invariants of the target, or the engine throws a <code>TypeError</code>. For example:</p>
<ul>
<li><code>get</code> must return the actual value for a <strong>non-writable, non-configurable</strong> data property.</li>
<li><code>has</code> can't hide a non-configurable property.</li>
<li><code>ownKeys</code> must include all non-configurable own keys, and must not add keys if the target is non-extensible.</li>
</ul>

<h2 id="performance-and-pitfalls">Performance and pitfalls</h2>
<ul>
<li><strong>Proxies are slower</strong> than plain property access because traps defeat many engine optimisations (inline caches). Don't put them in hot inner loops.</li>
<li><strong>Identity:</strong> <code>proxy !== target</code>. Code that uses objects as <code>Map</code> keys or does <code>===</code> checks can break.</li>
<li><strong>Private fields don't work through proxies.</strong> <code>#field</code> access checks the <em>actual</em> object, and the proxy isn't the instance:</li>
</ul>

<p>Fix it by binding methods to the target in the <code>get</code> trap when the value is a function.</p>
<ul>
<li><strong>Built-ins with internal slots</strong> (<code>Map</code>, <code>Set</code>, <code>Date</code>, typed arrays) have the same problem — their methods need <code>this</code> to be the real object.</li>

<h2 id="conclusion">Conclusion</h2>
<p>Use <code>Reflect</code> to forward every trap with its receiver, respect the invariants, and keep proxies out of hot paths. Follow those rules and proxies give you validation layers, observable state, API versioning shims and sandboxing without changing the code that uses the object.</p>
