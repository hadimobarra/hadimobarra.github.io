10:T4741,<h2 id="the-pixel-pipeline">The pixel pipeline</h2>
<p>Every frame the browser produces goes through up to five stages:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-text">JavaScript → Style → Layout → Paint → Composite
</code></pre><span class="code-lang">text</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<ol>
<li><strong>JavaScript</strong> — your code (or CSS animations/transitions) changes something.</li>
<li><strong>Style</strong> — the browser works out which CSS rules apply to which elements and computes final styles.</li>
<li><strong>Layout</strong> — it calculates the geometry of every affected box: size and position.</li>
<li><strong>Paint</strong> — it records drawing commands (text, colours, borders, shadows, images) for each layer.</li>
<li><strong>Composite</strong> — layers are rasterised (often on the GPU) and assembled into the final image.</li>
</ol>
<p>At 60Hz you have <strong>16.7ms per frame</strong> for all of this, and in practice closer to 10ms of budget for your own work. At 120Hz it's 8.3ms.</p>
<p>The key optimisation insight: <strong>later stages are cheaper, and you can skip earlier ones.</strong></p>

<h2 id="layers-and-will-change">Layers and <code>will-change</code></h2>
<p>To composite an element on its own, the browser must promote it to a <strong>layer</strong>. Elements with active transform/opacity animations get promoted automatically, but promotion at animation start can cause a one-frame hitch. <code>will-change</code> tells the browser ahead of time:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-css"><span class="hljs-selector-class">.card</span><span class="hljs-selector-pseudo">:hover</span> { <span class="hljs-attribute">will-change</span>: transform; }
</code></pre><span class="code-lang">css</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<p>Use it sparingly:</p>
<ul>
<li>Every layer costs GPU memory. Putting <code>will-change: transform</code> on hundreds of list items can make performance <em>worse</em>, especially on mobile.</li>
<li>Prefer adding it just before an animation (on hover, or from JS right before starting) and removing it afterwards.</li>
<li>Layer promotion changes stacking and can affect text anti-aliasing.</li>
</ul>
<h2 id="forced-synchronous-layout-layout-thrashing">Forced synchronous layout (layout thrashing)</h2>
<p>Browsers batch style and layout work until the end of the frame. But if you <strong>read</strong> a layout property (<code>offsetHeight</code>, <code>getBoundingClientRect()</code>, <code>scrollTop</code>…) after <strong>writing</strong> a style, the browser must calculate layout immediately to give you a correct answer.</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-js"><span class="hljs-comment">// ❌ Each iteration: write → read → forced layout</span>

<h2 id="the-flip-technique">The FLIP technique</h2>
<p>Some animations seem to require animating layout — reordering a list, expanding a card into a modal. <strong>FLIP</strong> (First, Last, Invert, Play) turns them into cheap transforms:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-js"><span class="hljs-keyword">function</span> <span class="hljs-title function_">flip</span>(<span class="hljs-params">element, mutate</span>) {
  <span class="hljs-comment">// First: record the starting position</span>
  <span class="hljs-keyword">const</span> first = element.<span class="hljs-title function_">getBoundingClientRect</span>();

  <span class="hljs-comment">// Apply the DOM/layout change instantly</span>
  <span class="hljs-title function_">mutate</span>();

  <span class="hljs-comment">// Last: record the final position</span>
  <span class="hljs-keyword">const</span> last = element.<span class="hljs-title function_">getBoundingClientRect</span>();

  <span class="hljs-comment">// Invert: move it back to where it started using a transform</span>
  <span class="hljs-keyword">const</span> dx = first.<span class="hljs-property">left</span> - last.<span class="hljs-property">left</span>;
  <span class="hljs-keyword">const</span> dy = first.<span class="hljs-property">top</span> - last.<span class="hljs-property">top</span>;
  <span class="hljs-keyword">const</span> sx = first.<span class="hljs-property">width</span> / last.<span class="hljs-property">width</span>;

<h2 id="paint-cost-is-real-too">Paint cost is real too</h2>
<p>Even without layout, some paints are expensive:</p>
<ul>
<li>Large <code>box-shadow</code> and <code>filter: blur()</code> values, especially when animated.</li>
<li><code>backdrop-filter</code> over large or frequently changing areas.</li>
<li>Huge areas invalidated by small changes. Use DevTools → Rendering → <strong>Paint flashing</strong> to see what repaints.</li>
</ul>
<p>A useful trick for animated shadows: put the shadow on a pseudo-element and animate its <code>opacity</code> instead of the shadow itself.</p>
