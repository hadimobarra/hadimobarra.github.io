10:T12a0,<h2 id="two-kinds-of-components-one-tree">Two kinds of components, one tree</h2>
<p>React Server Components (RSC) split your component tree across two environments:</p>
<ul>
<li><strong>Server Components</strong> run only on the server (at build time or request time). They can be <code>async</code>, read databases and files directly, and <strong>ship zero JavaScript</strong> to the browser.</li>
<li><strong>Client Components</strong> are the components you already know. They are marked with <code>"use client"</code>, run on the server for the initial HTML <em>and</em> in the browser, and can use state, effects and event handlers.</li>
</ul>
<p>In the Next.js App Router, every component is a Server Component unless something makes it a client one.</p>

<h2 id="use-client-marks-a-boundary-not-a-component"><code>"use client"</code> marks a boundary, not a component</h2>
<p>The directive marks a <strong>module boundary</strong>: that file and everything it <em>imports</em> become part of the client bundle. That's why you should push <code>"use client"</code> as far down the tree as possible — mark the small interactive leaf, not the whole page.</p>
<p>A frequent mistake is putting <code>"use client"</code> at the top of a layout because one child needs <code>useState</code>. Now every import of that layout — markdown parsers, date libraries, icon sets — ships to the browser.</p>
<h2 id="what-actually-goes-over-the-wire">What actually goes over the wire</h2>
<p>Server Components don't render to HTML in the browser; they render to the <strong>RSC payload</strong>, a streamable serialised description of the tree. Conceptually it looks like:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="language-text">0: ["$", "ul", null, { children: ["$L1", "$L2"] }]
1: ["$", "li", null, { children: [["$", "h2", null, { children: "Hello RSC" }],
     ["$", "$Lclient:LikeButton", null, { postId: "1", initialLikes: 3 }]] }]
client:LikeButton: { id: "./like-button.js", chunks: ["chunk-abc.js"] }
</code></pre><span class="code-lang">text</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<p>Server Component output is inlined as plain elements. Client Components appear as <strong>references</strong> to a module plus the props to pass them. The browser downloads only those referenced chunks and hydrates them.</p>
<p>Two consequences follow:</p>
<ol>
<li><strong>Props passed from server to client must be serialisable</strong> — plain objects, arrays, strings, numbers, <code>Date</code>, <code>Map</code>, <code>Set</code>, promises and server actions. Not class instances, and not ordinary functions.</li>
<li><strong>Navigations fetch payloads, not HTML.</strong> On client navigation, React requests the RSC payload for the new route and merges it into the existing tree, so client state in shared layouts survives.</li>
</ol>
<h2 id="the-composition-rule-pass-server-components-as-children">The composition rule: pass Server Components as children</h2>
<p>A Client Component can't <em>import</em> a Server Component (the import would pull server-only code into the client bundle). But it can <em>render</em> one passed in as a prop:</p>
<div class="code-block" dir="ltr"><pre tabindex="0"><code class="hljs language-tsx"><span class="hljs-comment">// ❌ Inside a client component file</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">ServerSidebar</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"./server-sidebar"</span>; <span class="hljs-comment">// becomes client code</span>

<span class="hljs-comment">// ✅ Compose from a server component instead</span>
<span class="hljs-comment">// app/layout.tsx (server)</span>
<span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">CollapsiblePanel</span>></span>          {/* client: owns open/closed state */}
  <span class="hljs-tag">&#x3C;<span class="hljs-name">ServerSidebar</span> /></span>          {/* server: rendered on the server, passed as children */}
<span class="hljs-tag">&#x3C;/<span class="hljs-name">CollapsiblePanel</span>></span></span>
</code></pre><span class="code-lang">tsx</span><button type="button" class="code-copy" data-copy-code="" aria-label="Copy code"><svg width="14" height="14" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" aria-hidden="true"><rect x="9" y="9" width="13" height="13" rx="2"></rect><path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path></svg></button></div>
<p><code>children</code> here is already-rendered output in the RSC payload, so the client component just places it. This "donut" pattern — an interactive shell around server-rendered content — is the most important RSC composition technique.</p>

<h2 id="mutations-with-server-actions">Mutations with Server Actions</h2>

<p><strong>Treat every Server Action as a public API endpoint.</strong> Anyone can call it with any arguments. Authenticate, authorise and validate inside the action itself — never rely on the UI hiding a button.</p>
<h2 id="pitfalls-checklist">Pitfalls checklist</h2>
<ul>
<li><strong>Leaking secrets:</strong> a module imported by a client component can end up in the browser. Add <code>import "server-only"</code> to modules that touch secrets so the build fails if that happens.</li>
<li><strong>Context:</strong> <code>createContext</code> providers must be Client Components. Wrap them in a small client <code>Providers</code> component and render it from your server layout.</li>
<li><strong>Over-fetching in loops:</strong> use React's <code>cache()</code> to dedupe the same data request across components within a single render.</li>
<li><strong>Large props:</strong> everything you pass to a client component is serialised into the payload. Pass the 3 fields it needs, not the full database row.</li>
</ul>
<h2 id="conclusion">Conclusion</h2>
<p>Server Components render to a serialisable stream. Client Components are references in that stream that hydrate in the browser. <code>"use client"</code> marks a bundle boundary, and composition through <code>children</code> lets server content live inside interactive shells. Suspense streams the slow parts, and Server Actions handle mutations as public endpoints. Keep <code>"use client"</code> at the leaves, fetch in parallel and validate every action, and RSC will give you smaller bundles and faster pages.</p>
