10:Tdce,<h2 id="why-checklists-dont-help">Why checklists don't help</h2>
<p>"Compress images, split code, use a CDN" is true for every site and useful for none in particular. A list can't tell you which of its twenty items is slowing down <em>your</em> page. A workflow can.</p>
<p>Here is one, in five steps. The examples come from <a href="/projects/this-website/">this site</a>.</p>
<h2 id="step-1-know-the-three-targets">Step 1: know the three targets</h2>
<div class="table-wrap" tabindex="0"><table>
<thead>
<tr>
<th>Metric</th>
<th>Question it answers</th>
<th>Good</th>
<th>Poor</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>LCP</strong></td>
<td>When does the main content appear?</td>
<td>≤ 2.5 s</td>
<td>> 4 s</td>
</tr>
<tr>
<td><strong>INP</strong></td>
<td>How fast does the page react?</td>
<td>≤ 200 ms</td>
<td>> 500 ms</td>
</tr>
<tr>
<td><strong>CLS</strong></td>
<td>Does the layout jump?</td>
<td>≤ 0.1</td>
<td>> 0.25</td>
</tr>
</tbody>
</table></div>
<p>They're judged at the <a href="https://web.dev/articles/vitals">75th percentile</a> of real visits. INP replaced First Input Delay in March 2024, so advice about FID is out of date. FID only looked at the delay before the first input; INP covers whole interactions during the whole visit.</p>
<h2 id="step-2-measure-users-then-reproduce-in-the-lab">Step 2: measure users, then reproduce in the lab</h2>
<p>Field data tells you <em>what</em> is slow, and for whom. Lab data tells you <em>why</em>. You need both, in that order.</p>

<p>The <a href="https://github.com/GoogleChrome/web-vitals">web-vitals</a> attribution build tells you which element or interaction was responsible. If you have enough traffic, the <a href="https://developer.chrome.com/docs/crux">Chrome UX Report</a> has field data without any code.</p>
<p>In the lab, repeat every measurement. Eight Lighthouse runs of this site's homepage gave between 280 and 700 ms of blocking time. If you run it once before and once after a change, you're comparing noise.</p>

<li><strong>Load delay.</strong> Time before the browser even <em>starts</em> fetching the main resource. Usually the largest part, and the most ignored.</li>
<li><strong>Load time.</strong> The download. This is the only part image compression improves.</li>
<li><strong>Render delay.</strong> Everything is here, and something stops it being painted: CSS, fonts, or JavaScript.</li>
</ul>
<p>If the main image is found late, tell the browser early, and never lazy-load it:</p>

<p>If the largest element is <em>text</em>, as on this site, images don't matter at all. Here the cause was render delay: text started at <code>opacity: 0</code> and waited for a script to animate it in. Making content visible by default, as part of a wider rebuild, moved LCP from 4.2 s to around 2 s. No image was the cause.</p>
<h3 id="inp-has-three-parts">INP has three parts</h3>
<p>Input delay, processing and presentation, each with a different fix. I cover them in <a href="/blog/taming-inp-interaction-to-next-paint/">Taming INP</a>, with a demo you can feel.</p>
<h3 id="cls-is-a-list-of-culprits">CLS is a list of culprits</h3>
<p>Each shift has a source. The usual ones:</p>
<ul>
<li>Images and embeds without <code>width</code> and <code>height</code>.</li>
<li>Content inserted above what the user is reading: banners, late ads.</li>
<li>Web fonts that swap in with different metrics.</li>
</ul>
<p>The last is the hardest to see, because it depends on the fonts installed on the visitor's device. My own machine showed a CLS of zero, while a CI runner measured 0.14 for the same build. The <a href="/blog/less-javascript-same-blocking-time/">full story</a> is worth a read before you trust a local number.</p>
<h2 id="step-4-fix-the-largest-part-and-re-measure">Step 4: fix the largest part, and re-measure</h2>
<p>One change at a time, or you won't know which one worked. Write the expected effect down first:</p>
<blockquote>
<p>Inlining the critical CSS should cut render delay by about 300 ms on mobile.</p>
</blockquote>
<p>If the result disagrees with the prediction, your model of the page is wrong. That is worth more than the 300 ms.</p>
<p>Some things that often turn out to be the largest part:</p>
