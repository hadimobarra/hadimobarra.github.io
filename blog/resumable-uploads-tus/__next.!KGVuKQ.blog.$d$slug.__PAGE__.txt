12:T520,<h2 id="the-problem-with-one-big-request">The problem with one big request</h2>
<p>Uploading a file is one line of code, until the file is large. A 3 GB CSV over a 20 Mbit/s connection takes about twenty minutes. Somewhere in those minutes a laptop sleeps, a VPN reconnects or a proxy times out. With a single <code>POST</code>, all progress is lost.</p>
<p>I built an upload module for a data platform, designed for files of several gigabytes. This article covers the ideas behind it. The demo is a separate example that uses the same libraries.</p>
<h2 id="why-just-split-it-into-chunks-isnt-enough">Why "just split it into chunks" isn't enough</h2>
<p>The obvious fix is to slice the file and send the pieces. Then the questions begin. Which pieces arrived? What if a piece arrived but its response didn't? Who deletes the pieces of an upload nobody finished?</p>
<p>Those are protocol questions, and answering them privately means maintaining both ends forever. <a href="https://tus.io/protocols/resumable-upload">TUS</a> is an open protocol that answers them, with clients and servers in many languages. The IETF is standardizing the same idea as <a href="https://datatracker.ietf.org/doc/draft-ietf-httpbis-resumable-upload/">resumable uploads for HTTP</a>.</p>

<h2 id="decisions-on-the-client">Decisions on the client</h2>
<h3 id="the-server-is-the-only-source-of-truth">The server is the only source of truth</h3>
<p>A progress bar shows bytes <em>sent</em>. Bytes sent aren't bytes stored: some were in flight when the connection died. Never resume from the progress value. Ask.</p>
<h3 id="never-load-the-file-into-memory">Never load the file into memory</h3>
<p><code>File</code> is a <code>Blob</code>, and <code>Blob.slice()</code> is lazy. It returns a view without reading anything, so a resumed upload of a 3 GB file costs almost no memory:</p>

<p>Not every failure deserves a retry. A <code>403</code> will be a <code>403</code> again in five seconds. Network errors, <code>409</code>, <code>423</code> and <code>5xx</code> are worth retrying; other <code>4xx</code> responses aren't.</p>
<h3 id="pausing-is-not-failing">Pausing is not failing</h3>
<p>A user who presses pause and a network that disappears look similar to the code, but mean different things. One should wait without limit. The other should retry. Keep them as separate states in the interface too, so nobody wonders whether anything is happening:</p>

<h3 id="do-you-need-chunks-at-all">Do you need chunks at all?</h3>
<p>TUS doesn't require them. One <code>PATCH</code> can carry the whole remainder, and the server keeps what it received if it breaks. Set <code>chunkSize</code> only when something in between forces you to, such as a proxy with a body limit. Small chunks add a round trip each.</p>
<h2 id="what-the-server-has-to-do">What the server has to do</h2>
<ul>
<li>Store the offset durably <em>before</em> acknowledging it.</li>
<li>Reject a <code>PATCH</code> whose offset doesn't match.</li>
<li>Expire unfinished uploads, or storage fills with halves of files.</li>
<li>Check that the user resuming an upload is the one who created it. The URL alone must not be a permission.</li>
</ul>
<h2 id="conclusion">Conclusion</h2>
<p>Resuming isn't a feature you add to an upload. It's a question, "how much do you have?", asked of the only party that knows. Once the protocol asks it, pause, retry and recovery stop being special cases.</p>
